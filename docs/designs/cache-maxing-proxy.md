## Problem Statement

Stateless LLM clients silently destroy prefix-cache hits on every backend. The ds4 article (DeepSeek V4 Flash on M3 Ultra, 12x warm-turn speedup) proved the mechanism: engines only extend a cached prefix when the next request is an exact token-level extension. Real clients break this three ways: (1) they regenerate assistant replies from their own history instead of replaying the exact sampled text — one whitespace or tool-call serialization difference and the cache misses from that token on; (2) they reorder/reformat system prompts and tool definitions between turns; (3) they never warm the cache before the first real question. Adrian fixed this by hand for one client. Every other client does it wrong, against every backend that prefix-caches — which is now all of them (Anthropic, OpenAI, DeepSeek bill cached input tokens ~10x cheaper; vLLM, llama.cpp, mlx-lm all prefix-cache locally).

cache-maxing: an OpenAI-compatible proxy daemon that normalizes prompt formatting so prefix caches actually hit, with prefix-affinity routing and hit-rate/cost observability. Point your client at localhost; everything gets faster and cheaper.

## What Makes This Cool

- The launch post writes itself: "A 12x speedup everyone leaves on the table because clients format prompts wrong — we fixed it for everyone."
- Immediate dollar savings on cloud inference: prefix-sticky routing keeps a prefix family on the provider that already holds it warm (naive load-balancing across providers destroys provider-side caches). The founder's own OmniRoute traffic is the first testbed.
- Cross-platform and engine-agnostic: works in front of OmniRoute, vLLM farms, mlx-lm, LM Studio, any OpenAI-compatible endpoint. The MLX daemon (sibling repo) is one deep-integration target, not a limit.
- The hit-rate dashboard shows exactly which message/turn broke the prefix — a diagnostic nobody offers today.

## Constraints

- Matching must happen in token space: the proxy needs the backend's tokenizer to verify a prefix match (obtainable from local engines; approximate with the model's public tokenizer for cloud APIs).
- Replay-the-reply must be strictly conditional: splice the remembered reply only when the client's version is semantically identical (same call IDs, ordering, JSON-equivalent arguments). Never overwrite actual content changes — Codex flagged this, it's a correctness invariant.
- Streaming (SSE) is the primary client mode for coding agents — the proxy must pass streams through unbuffered while still recording exact token sequences.
- Secrets never stored: API keys pass through, never logged. Request/response bodies are recorded only with explicit opt-in to trace capture — v0 (the founder's own traffic) runs with opt-in ON for the founder's own machine; the shipped default is opt-in OFF with ephemeral in-memory observation only.

2. A proxy can deliver most of the cache value without forking any engine. — agreed

## Approaches Considered

### Approach A: Universal cache-normalizing proxy (recommended)
Daemon exposing BOTH the OpenAI API (`/v1/chat/completions`, `/v1/completions`) and the Anthropic Messages API (`/v1/messages`) in v1 — clients speak whichever dialect they already speak; the proxy translates between dialects internally when routing to a backend of the other kind. Records exact token sequences sent and replies received per session; rewrites the next request so the prompt is a clean extension (verbatim reply splice when semantically identical, normalized tool-call serialization, stable message ordering); prefix-affinity routing across configured backends; optional cache warming; hit-rate/cost observability. Effort S→M, Risk Low. Works with every backend day one. Warming is backend-specific (see binding rules below) — the ds4 `max_tokens:0` trick works on local engines but most cloud APIs require max_tokens ≥ 1, so cloud warming is demoted to open question until verified against the v0 backend.

### Approach B: MLX/macOS daemon first (original framing)
KV-level cache management for Apple Silicon only. Effort L, Risk Medium. Deferred to sibling repo (mlxcache): deeper value but smaller initial audience and no cloud savings.

### Approach C: Engine-specific patches
Ship client-side fixes per agent tool (a patched client, a plugin). Rejected during session: fragmentation, per-client maintenance treadmill, no cross-client value; the proxy is the general fix.

## Recommended Approach

**A — universal cache-normalizing proxy — sequenced per Codex's gate: prove a safely repairable formatting defect produces meaningful savings on one real client before building out generality.**

1. **v0 (the gate, days):** one real coding agent client through the proxy to one cloud backend via OmniRoute. Observe (capture messages, first divergence point, cached_tokens, TTFT, billed cost — with trace-capture opt-in ON, founder's own machine). Repair the tool-call-argument formatting defect. Replay captured multi-turn traces with repair on/off; report cache reuse, total cost, latency, tool-call correctness.
2. **v1 (weeks):** if v0 shows meaningful savings: dual-dialect endpoints (OpenAI + Anthropic, with cross-dialect translation), verbatim reply splicing, stable ordering, prefix-affinity routing across the user's configured backends, backend-specific warming, per-session backend pinning.
3. **v1.5:** hit-rate dashboard (which turn broke the prefix, cached vs billed tokens per request), trace capture/replay as a first-class feature.
4. **v2:** the MLX daemon (sibling repo) implements the same policy core with KV persistence; this proxy becomes its universal front door.

### Contract rules resolved by review (binding)

- **Primary v0 metric (R1-5):** billed-at-full-rate input tokens — computed as `prompt_tokens − cached_tokens` from the backend's usage fields (OpenAI/Anthropic report both). One metric, one formula, pass/fail on the ≥30% reduction.
- **Replay protocol (R1-4, refined R2-2):** cloud backends expose no cache namespaces, so the baseline protocol is: verify the provider's cache TTL empirically first; time-gap all runs by more than that TTL; each measured run is preceded (after the time gap) by an identical discard run so BOTH arms — repair-on and repair-off — start from an identically discard-warmed cache state. The comparison is warm-start-to-warm-start, not cold. Same request order each run; both run orders (repair-on first and repair-off first) reported to expose order effects.
- **Stream reassembly (R1-6):** streamed responses are reassembled via delta accumulation (text deltas concatenated; tool-call argument fragments accumulated per index) and the stored record must byte-match what the client ultimately received. Streams pass through to the client unbuffered while the record builds.
- **Session identity (R1-7, refined R2-1):** v1 session key = hash of the *normalized* stable conversation prefix — the proxy's canonical serialization of the system prompt + first user message, taken AFTER the proxy's own normalization stage (never on the client's raw bytes, or reformatting clients would fragment their own sessions) — plus client source address. Affinity map persists across proxy restarts in the SQLite store. Exact keying is an open question if real traces show collisions.
- **Primary v0 metric per backend (R1-5, refined R2-3):** billed-at-full-rate input tokens, computed from each backend's NATIVE usage fields: OpenAI = `prompt_tokens − prompt_tokens_details.cached_tokens`; Anthropic = `usage.input_tokens` (already excludes cached tokens — do NOT subtract again) with `cache_creation_input_tokens` accounted separately at its write premium (1.25x) — the headline gate metric is the OpenAI-style uncached figure; on Anthropic the gate additionally reports total dollar cost including the cache-write premium so warming spend cannot hide. Pass/fail on ≥30% reduction of the headline metric.
- **Rewrite failure fallback (R1-8):** on any rewrite/splice failure or ambiguous semantic-identity check, send the client's original request unmodified and log the divergence for the dashboard. The proxy never breaks a request it cannot improve.
- **Ordering normalization (R1-9):** only stabilizes ordering among independent messages (system prompts, tool definitions); API-mandated adjacency is preserved (tool results immediately follow their assistant tool_calls).
- **Task boundary (R1-10):** the value metric aggregates per session, not per "task": a session is delimited by an idle gap > 5 minutes in the request stream (tunable). Per-session cost and p95 are the reported units.
- **Dual-dialect endpoints (v1 scope, user-directed):** serve both OpenAI (`/v1/chat/completions`, `/v1/completions`, streaming SSE in OpenAI chunk format) and Anthropic (`/v1/messages`, SSE in Anthropic event format: message_start, content_block_delta, message_stop). Translation is symmetric: an OpenAI-dialect client can reach an Anthropic backend and vice versa; tool-call schemas translate (OpenAI `tool_calls`/`tool_choice` ↔ Anthropic `tools`/`tool_use`/`tool_result` blocks). Cached-token usage fields normalize to a common internal record (OpenAI `usage.prompt_tokens_details.cached_tokens` ↔ Anthropic `usage.cache_read_input_tokens`/`cache_creation_input_tokens`). v0 remains single-client/single-backend on whichever dialect that pair uses; dual-dialect lands in v1.

## Open Questions

- Which cloud backend for v0? (Anthropic bills cached tokens distinctly — cleanest measurement; founder's OmniRoute config decides.)
- Tokenizer acquisition for cloud backends: public tokenizer approximation vs provider prefix-report APIs — measure the mismatch rate on real traces.
- How to identify "semantically identical" tool-call arguments robustly (JSON canonicalization? token-level diff with threshold?)
- Does OmniRoute itself want this as a feature instead of a sibling proxy? (founder decision — building it standalone first preserves both options)
- Cloud cache warming: is there a provider-sanctioned prefill/priming mechanism, and does `max_tokens: 1` + immediate stop actually warm provider caches? Verify against the v0 backend before committing.

## Success Criteria

- v0 gate: on replayed real multi-turn traces from the founder's own agent traffic, repair-on shows ≥ 30% reduction in billed-at-full-rate input tokens (per-backend native-field formula in the contract rules; dollar-cost variant reported alongside on Anthropic to expose cache-write premium) with zero tool-call correctness regressions.
- v1: a client speaking each dialect (OpenAI and Anthropic) runs through the proxy against backends of both kinds with zero client changes; cached-token accounting is correct in both directions (normalized usage record verified against each backend's native fields).
- Hit-rate dashboard explains every cache miss on a captured trace: the divergent message is identified, not guessed.
- Per-session value (premise 4, the actual goal): p95 turn latency and per-session billed cost on warm sessions measurably lower than the repair-off baseline on the same traces (time-gapped replay protocol above, both run orders reported).
- One public artifact: the before/after replay post (the ds4 article is the citation; cache-maxing is the general fix).

### R3-1 — consistency

**Problem**

> The two 'Primary v0 metric' contract bullets contradict each other. The original R1-5 bullet still reads 'computed as prompt_tokens − cached_tokens from the backend's usage fields (OpenAI/Anthropic report both)', while the R2-3 refinement bullet two items later states Anthropic's input_tokens 'already excludes cached tokens — do NOT subtract again'. A reader implementing from the first bullet double-subtracts on Anthropic, exactly the R2-3 defect the second bullet fixed.

**Remedy**

> Delete or rewrite the stale R1-5 bullet so the document carries only the per-backend native-field formula (or reduce to a pointer to the refined bullet).

### R3-2 — consistency

**Problem**

> Premise 4 still defines the value metric as 'total cost + p95 latency per completed task', but the binding Task boundary rule (R1-10) explicitly redefines aggregation 'per session, not per task' (idle gap > 5 minutes), and Success Criteria report per-session values. The document states the unit two different ways.

**Remedy**

> Update premise 4 to say 'per session' (or 'per session as a task proxy') so the premise matches the binding rule it cites.

### R3-3 — consistency

**Problem**

> The v0 gate passes/fails solely on the headline uncached-input metric, while the Anthropic dollar-cost variant (including the 1.25x cache-write premium) is only 'reported'. Repair-on can add cache_creation writes whose premium exceeds the read savings, so the gate can pass while total spend worsens — contradicting the bullet's own stated purpose that the dollar figure exists 'so warming spend cannot hide'. Reporting without gating lets it hide.

**Remedy**

> State explicitly whether the dollar-cost variant is a gate condition (e.g., pass requires headline ≥30% reduction AND no total-dollar regression) or advisory-only; if advisory, drop the 'cannot hide' claim.

### R3-4 — consistency

**Problem**

> The replay protocol mandates a discard run before every measured run but never states whether the discard run's usage counts in the ≥30% gate metric, while premise 4 requires 'A/B traces must count every request including warming traffic'. Discard runs are warming traffic; whether their billed tokens are inside or outside the gate metric is undefined, and the two rules can be read to disagree.

**Remedy**

> State the accounting: either discard-run usage is included in each arm's metric (symmetric, so the comparison stays fair) or explicitly excluded from the gate and reported separately — and reconcile with premise 4's 'count every request' wording.

### R3-5 — feasibility

**Problem**

> The dual-dialect rule claims translation 'is symmetric' between OpenAI and Anthropic APIs, but several OpenAI request features have no Anthropic equivalent (e.g., n>1, logprobs, response_format/JSON mode, parallel_tool_calls control) and several fields map non-trivially (top-level system vs system message, required Anthropic max_tokens, tool_choice shapes, role:'tool' → user tool_result blocks). 'Symmetric' overclaims; behavior for unsupported or lossy features is unspecified, which is where proxy correctness breaks.

**Remedy**

> Define the translatable feature subset for v1 and specify the fallback for anything outside it (reject with a clear error, degrade, or emulate), mirroring the rewrite-failure rule.

### R3-6 — completeness

**Problem**

> v1 commits to per-session backend pinning and prefix-affinity routing but never specifies behavior when the pinned backend is down, rate-limited, or no longer serves the pinned model. The choice (fail the request, reroute and accept a cold cache plus re-warm cost, or queue) materially affects both the value metric and reliability and is a required behavior of the committed routing design.

**Remedy**

> Specify pinned-backend failure behavior: at minimum whether pinning is strict (fail) or best-effort (reroute + re-warm), and how the session's affinity record updates after failover.

### R3-7 — clarity

**Problem**

> The rewrite failure fallback's user-visible behavior is unspecified: the client's original request is sent unmodified and the divergence is logged for the dashboard, but nothing says whether the user is warned (response header, log line, dashboard-only) that repair was skipped. Silent pass-through and visible warning are both defensible; which one ships is a decision the approver should see.

**Remedy**

> Choose and document whether the fallback is intentionally silent (dashboard-only) or surfaces a warning to the user, and note the choice in the fallback rule.
